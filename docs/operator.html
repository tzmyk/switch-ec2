操作者向け

switch-ec2 操作手順書

稼働中の EC2 を作り直さずに、RHEL のライセンスだけを PAYG から ELC へ切り替えるための手順書です。サーバーの中身・IP アドレスはそのまま引き継ぎます。

この作業は何をするのか

EC2 の ライセンス種別（課金コード）は、インスタンスを起動したときに使った AMI で決まり、後から変更できません。すでに動いているサーバーのライセンスだけを変えることはできない、ということです。

そこでこのツールは、次の手順でライセンスだけを入れ替えます。

  1. ELC ライセンスの AMI から、空っぽの新しい EC2 を起動する（この瞬間にライセンスが確定します）
  2. 新しい EC2 に最初から付いてきたディスクを取り外して捨てる
  3. 元のサーバーのディスク（OS ごと全部）とネットワークカードを、そのまま新しい EC2 に付け替える

結果として、中身は元のサーバーのまま、ライセンスだけが変わった EC2 ができあがります。OS の再インストールもデータ移行も行いません。

何が変わり、何が変わらないか

項目結果補足
OS・アプリ・データ変わらないディスクそのものを移すため。再インストール・コピーは一切しません
プライベート IP アドレス変わらないネットワークカードごと移すため
Elastic IP変わらないネットワークカードに紐づいているため自動的に付いてきます
MAC アドレス変わらない同上
セキュリティグループ変わらない同上
インスタンスタイプ・タグ・IAM ロール変わらない元の設定を読み取って新しい EC2 に再設定します
ライセンス（課金コード）変わるこれが作業の目的です
インスタンス ID変わる要注意。下の警告を参照してください
自動割り当てのパブリック IP変わるElastic IP を使っていない場合、パブリック IP は別の値になります
EBS ボリュームに付けたタグ消える場合がある切り戻しを行った場合のみ。ボリュームのタグは引き継がれません
インスタンス ID が変わることの影響

インスタンス ID（i-0abc...）は必ず新しい値になります。次のものは ID を見て動いているため、作業後に設定し直す必要があります。スクリプトはこれらを自動で直しません。

  • CloudWatch のアラーム
  • ロードバランサーのターゲットグループへの登録
  • Auto Scaling グループへの登録
  • AWS Backup・DLM の対象指定（タグで指定している場合は影響しません）
  • SSM の管理対象、監視 SaaS の登録、社内の管理台帳・CMDB

作業前に「このサーバーの ID を参照している設定」を洗い出しておいてください。

作業の全体像と所要時間

作業は CloudShell（AWS のブラウザ上のターミナル）だけで行います。番号付きのスクリプトを、番号順に実行するだけです。スクリプトは対象サーバーの中にはログインしません。

順番やること所要時間の目安サービス停止
101_prepare.sh — 今の設定を全部記録して、切替できるか検査約 40 秒/台なし
202_backup.sh — バックアップ AMI を作成3〜10 分再起動あり
303_switch.sh — 切替の本体約 7〜11 分/台停止あり
404_verify.sh — 切替結果を検査約 30 秒/台なし
サービスが止まるタイミングは 2 回

1 回目：手順 2 のバックアップ AMI 作成時に再起動が入ります（整合性を確保するためです）。
2 回目：手順 3 の切替本体で、停止 → 起動が入ります。約 7〜11 分です。

複数台を対象にする場合、手順 2 では全台がほぼ同時に再起動します。クラスタを組んでいて同時再起動が許されない構成では、targets.txt を分けて別々に実行してください。

CloudShell の制約 実行前に必ず読む

CloudShell は放置すると勝手に終了します

CloudShell は、キーボードやマウスの操作がない状態が約 20〜30 分続くとセッションを終了します。スクリプトが動いていることは「操作」とみなされません。画面を眺めているだけ、別のタブを見ている、といった状態では切られます。

セッションが終了すると、実行中のスクリプトは強制的に止まります。

必ず守ってほしい 2 つのこと

1ホームディレクトリで作業する

CloudShell で保存されるのは ホームディレクトリ（/home/cloudshell-user）の中だけです。それ以外の場所に置いたファイルは、セッションが終わると消えます。

このツールは作業の記録を work/ フォルダに保存し、トラブル時の復旧はこの記録が頼りです。記録が消えると復旧が非常に困難になります。

# 実行前に必ず確認する。/home/cloudshell-user で始まっていれば OK
pwd

2実行中はターミナルを操作し続ける

待っている間、ときどきキーを押す（何も入力しない Enter でも構いません）などして、操作がある状態を保ってください。

これが中断を防ぐ唯一の実効的な手段です。複数台をまとめて処理する場合は実行時間が長くなるので、絶対に放置しないでください。

複数台をまとめて処理する場合

対象台数と作業できる時間枠の都合上、1 回の実行で複数台を対象にすること、および --parallel（同時処理）の使用は問題ありません。そのうえで、次のことを知っておいてください。

やり方所要時間中断されたときの影響
1 台ずつ（既定）台数 × 7〜11 分中途半端になるのは常に 1 台だけ
--parallel で同時処理「最も遅い 1 台分 ＋ 順番待ち」に近づく手作業での復旧が必要なサーバーが同時に複数発生しうる
 
# config.env の MAX_PARALLEL 台まで同時処理（既定 4 台）
./03_switch.sh --parallel

# 同時処理する台数を明示する
./03_switch.sh --parallel=2
  • 台数が多い場合は、同時処理のほうが中断リスクの窓が短くなります。全体の実行時間が短くなるためです
  • 同時処理する台数は小さい値から始めてください。中断されたときに同時に対応しなければならないサーバーの数が、そのまま増えます
  • 同時処理でも記録とログはサーバーごとに分かれています。画面には全サーバーのログが混ざって流れますが、work/<サーバーのID>/03_switch.log を見れば 1 台分だけを追えます。復旧もサーバーごとに独立して行えます
  • 同時処理のときは、確認メッセージが最初に 1 回だけ出ます。先に全サーバーの事前検査を通すので、1 台でも検査に失敗すれば、どのサーバーも変更されません
もし中断されても、データは失われません

スクリプトは、元のサーバーを削除する前に、ディスクとネットワークカードを「削除されない設定」に変更し、ディスクを取り外し終えてから削除を実行します。どのタイミングで中断されても、ディスクとネットワークカードはデータごと AWS 上に残ります。

ただし自動では元に戻りません。中断されたら「途中で中断されたら」を見てください。

事前に確認・依頼すること

作業を始める前に、次の項目を関係者に確認してください。ここが埋まっていないと当日スクリプトが止まります。

ライセンス提供元に確認すること

  • ELC ライセンスの AMI ID（ami-...）。対象サーバーと同じリージョンにあること
  • 切替後に期待される課金コード（例：RunInstances:00g0）。任意ですが、設定しておくと検査が厳密になります
  • 切替後のサブスクリプション登録方法。カスタマーポータル直接／Satellite／アクティベーションキーのどれか。これが分からないと、切替後にセキュリティパッチが当てられない状態になります

サーバー管理者に確認すること

  • 対象サーバーが 起動中（running）であること。停止中のサーバーは対象にできません
  • 対象サーバーにインストールされているエージェント類の一覧（監視・バックアップ・ウイルス対策など）。インスタンス ID が変わることで再登録が必要なものがあります
  • 次の構成を使っていないこと。使っている場合は切替できません（スクリプトが検出して停止します）
    • スポットインスタンス／プレイスメントグループ／専有ホスト
    • ハイバネーション／Nitro Enclaves／マルチネットワークカード
    • 複数インスタンスに同時接続するディスク（Multi-Attach）
    • インスタンスストア（消えてしまうため。了承のうえ続行することは可能です）

自分で用意すること

  • 対象リソースを操作できる管理者権限（IAM ロールを使っているサーバーの場合、iam:PassRole も必要です）
  • OS 内の事前作業を行うため、対象サーバーへ SSH できる状態（鍵・セキュリティグループ）
  • 停止可能な時間帯の調整。再起動 1 回＋停止 7〜11 分が必要です
  • インスタンス ID を参照している設定の洗い出し（前述の警告を参照）
切替前に必ず行う OS 内の設定（忘れると SSH できなくなります）

インスタンス ID が変わると、OS の初期設定機能（cloud-init）が「新しいサーバーだ」と判断して、SSH のホスト鍵を作り直し、ホスト名を初期値に戻してしまいます。そうなると、接続元すべてで「ホスト鍵が違う」という警告が出て SSH が拒否されます。

これを防ぐため、対象サーバーの OS 内で、以下のファイルを作成しておいてください。

sudo tee /etc/cloud/cloud.cfg.d/99-switch-ec2.cfg <<'EOF'
ssh_deletekeys: false
preserve_hostname: true
EOF

この作業は手順 2（バックアップ AMI 作成）より前に行ってください。後から行うとバックアップ AMI にこの設定が入らず、切り戻しをしたときに同じ問題が起きます。

# 2. config.env を編集する

項目設定する内容

切替の手順

共通のルール

各スクリプトは必ずこの順番で実行してください。前のスクリプトが保存した記録を、次のスクリプトが使います。
失敗した場合はそのまま次に進まないでください。

1設定の記録と事前検査 CloudShell · 約 40 秒/台 · 停止なし

./01_prepare.sh

今のサーバーの設定を隅々まで記録し、切替できる構成かどうかを検査します。この時点では何も変更しません。安心して実行できます。

成功の見分け方：最後に 成功: 1 台 / 失敗: 0 台 と表示されること。

失敗したら：エラーメッセージに理由が書かれています。「非対応です」と出た場合は、その構成では切替できません。関係者に相談してください。

2バックアップ AMI の作成 CloudShell · 3〜10 分 · 再起動あり

./02_backup.sh

元のサーバーの完全なバックアップを AMI として作ります。切り戻しをするときはこの AMI を使います。

ここで対象サーバーが再起動します。停止可能な時間帯であることを確認してから実行してください。

成功の見分け方：AMI が available になりました と表示され、失敗: 0 台 で終わること。

3切替の実行 CloudShell · 7〜11 分/台 · 停止あり

./03_switch.sh

ここが本番です。元のサーバーは削除され、新しい EC2 に置き換わります。

実行すると確認メッセージが出るので、内容を読んで yes と入力してください。

この操作は取り消せません

元の EC2 は削除されます。同じ IP アドレスを引き継ぐには、元の EC2 を削除するしか方法がないためです。ディスクとネットワークカードは残るので、問題があれば切り戻せます。

実行中はターミナルを操作し続けてください。放置すると CloudShell に切られます。

成功の見分け方：切替完了: old=... new=... と表示され、所要時間の内訳が出ること。

4切替結果の検査 CloudShell · 約 30 秒/台 · 停止なし

./04_verify.sh

IP アドレス・ディスク・タグ・各種設定が引き継がれているか、ライセンスが変わったかを 1 項目ずつ検査します。読み取るだけで何も変更しません。

成功の見分け方：すべての行が [PASS] で、最後が PASS で終わること。

1 つでも [FAIL] があったら：内容を確認してください。特に UsageOperation の FAIL はライセンスが切り替わっていないことを意味し、作業の目的が達成できていません。

ここまで完了したら

切替は成功です。ただしまだ作業が残っています。「作業後に残っている作業」に必ず進んでください。特に OS 内のサブスクリプション再登録は、放置するとセキュリティパッチが当てられない状態が続きます。

切り戻しの手順

切替後に問題が見つかった場合、バックアップ AMI から元のライセンス（PAYG）のサーバーを復旧できます。

切り戻すとデータが巻き戻ります

復旧に使うのは手順 2 で作ったバックアップ AMIです。つまり、そのバックアップを取った時点までデータが戻ります。切替作業中および切替後に書き込まれたデータは失われます。

実行時に「巻き戻り時点」と「失われる書き込み期間」が表示されるので、必ず確認してください。

切替後に書き込まれたデータが入ったディスクは削除せずに残しますので、後からデータを取り出すことは可能です（下の注意を参照）。

# targets.txt の全対象を切り戻す
./05_rollback.sh

# 対象を絞って切り戻す（複数回指定できます）
./05_rollback.sh --target i-0123456789abcdef0

# 実行後に検査する
./06_verify_rollback.sh

05_rollback.sh は1 台ずつ順番に処理します（同時処理のオプションはありません）。複数台を切り戻す場合、所要時間は台数分かかります。

05_rollback.sh は、確認メッセージで次を表示します。内容を読んでから yes と入力してください。

  • 削除される切替後の EC2 の ID
  • 復旧に使うバックアップ AMI の ID
  • 巻き戻る時点と、そこから現在までの経過時間（＝失われる書き込みの期間）
  • 残しておくディスクの ID

所要時間は約 5〜6 分/台です。切替本体より少し短くなります。

成功の見分け方：切り戻し完了: と表示され、06_verify_rollback.sh がすべて [PASS] で終わること。

残したディスクを触るときの注意

切り戻しで残したディスクには Warning: DO-NOT-ATTACH-DUPLICATE-FS-UUID というタグが付いています。

これは、復旧したサーバーのディスクと、残したディスクの識別子が完全に同じためです。データを取り出したいからといって復旧したサーバーに直接つなぐと、識別子が重複して正しくマウントできず、危険です。必ず別のサーバーにつないでください。

切り戻し後の状態について

切り戻すと、OS の中身もバックアップを取った時点に戻ります。つまり切替後に行ったサブスクリプション再登録などの作業も元に戻ります（PAYG 用の設定に戻るので、パッチ適用は正常にできます）。

また、ディスクに付けていたタグは引き継がれません。ディスクのタグを条件にバックアップ設定などをしている場合は、付け直してください。切替前のタグは work/<元のID>/before_volumes.json に残っています。

症状別の対処

症状意味対処
インスタンスが running ではありません 対象サーバーが停止中・起動中など サーバーを起動してから 01 をやり直してください
〜は非対応です 切替できない構成を使っている その構成では切替できません。関係者に相談してください
BootMode 不一致 新しい AMI と元のサーバーの起動方式が違う そのまま進めると起動しなくなる恐れがあります。ライセンス提供元に AMI を確認してください
インスタンスストアがあります 引き継げないディスクがある そのディスクのデータは失われます。了承できる場合のみ、config.env で ALLOW_INSTANCE_STORE_LOSS=true を設定します
prepare 後に EBS 構成が変更されている 01 の実行後に、誰かがディスク構成を変えた 何が変わったか確認し、01 からやり直してください
UsageOperation が切替前後で変化していません ライセンスが切り替わっていない 指定した AMI がライセンス切替用のものか、提供元に確認してください。作業の目的が未達です
この対象は切り戻し済みのため再実行禁止です すでに切り戻し済みのサーバーに再度実行した 正常な保護動作です。AWS 側は何も変更されていません
03_switch.sh の完走証跡がありません 切替が最後まで終わっていない状態で切り戻そうとした 「途中で中断されたら」を参照してください

途中で中断されたら

まず落ち着いてください

ディスクとネットワークカードは必ず残っています。データが失われることはありません。やってはいけないのは、慌てて同じスクリプトを再実行することと、AWS コンソールから手動でサーバーを削除することです。

手順 1：どこまで進んだかを確認する

ログはリアルタイムで保存されているので、必ず残っています。

# 1 台を詳しく見る
tail -20 work/<元のインスタンスID>/03_switch.log

# 複数台をまとめて処理していた場合は、対象ごとの最終行を一覧できます
for d in work/*/; do
  printf '%s: %s\n' "$(basename "$d")" "$(tail -1 "$d/03_switch.log" 2>/dev/null)"
done

最後に ステップN ... 完了 と出ている行が、完了したところです。

手順 2：元のサーバーが残っているかを確認する

aws ec2 describe-instances --instance-ids <元のインスタンスID> \
  --query 'Reservations[].Instances[].State.Name' --output text
表示された状態意味次にすること
running / stopped元のサーバーはまだ残っています元に戻すことも、作業を続けることもできます。開発担当者に連絡してください
shutting-down / terminated元のサーバーは削除済みですディスクとネットワークカードは残っています。開発担当者に連絡して、手動で作業を続けてもらってください

手順 3：開発担当者に伝える情報

  • ログの最後の行（どのステップまで完了したか）
  • 手順 2 で確認した元のサーバーの状態
  • work/<元のインスタンスID>/ フォルダが残っていること
絶対にやらないこと
  • 同じスクリプトをそのまま再実行する（安全装置が働いて止まるようになっていますが、まず状況確認が先です）
  • AWS コンソールから手動でインスタンスやディスクを削除する（復旧できなくなります）
  • work/ フォルダを削除する（復旧の唯一の手がかりです）
切替がほぼ終わっていたのに中断された場合

04_verify.sh がすべて PASS するのに 05_rollback.sh が「完走証跡がありません」と言って止まる場合があります。これは切替の最後の記録だけが残らなかった状態です。次のコマンドで記録を作り直せます。

aws ec2 describe-instances \
  --instance-ids "$(cat work/<元のID>/new_instance_id.txt)" \
  > work/<元のID>/new_instance_after_switch.json

実行する前に必ず 04_verify.sh で切替が完了していることを確認してください。

作業後に残っている作業

1. OS の中で行う作業（重要）

サブスクリプションの再登録 — 検査が通ったらすぐに実施

切替前のライセンスで使っていたパッケージ配信サーバー（RHUI）は、ELC のサーバーからは使えません。そのままにすると dnf がエラーになり、セキュリティパッチが一切当てられない状態になります。

本案件では Satellite を使用します。登録の具体的な手順は専用の手順書に従ってください。この文書では扱いません。

やらなくてよいこと

同じディスク・同じネットワークカードを移しているため、次の作業は不要です。
/etc/machine-id／fstab やデバイス名の書き換え／ネットワーク設定／時刻同期の設定／authorized_keys

2. インスタンス ID を参照している設定の修正

作業前に洗い出しておいた項目（CloudWatch アラーム、ターゲットグループ、監視ツールの登録など）を、新しいインスタンス ID に更新してください。

3. 不要になったリソースの削除

スクリプトは何も自動削除しません。すべて課金され続けるので、検証が完了して問題ないと判断できたら、手動で削除してください。

対象目印いつ消してよいか
新 AMI に付いてきた不要なディスクタグ Purpose = switch-ec2-discarded-root検査がすべて PASS し、しばらく運用して問題ないと確認できたら
バックアップ AMI とスナップショットタグ Purpose = switch-ec2-backup切り戻す可能性がなくなったら。保持期間を決めておくことを推奨します
切り戻しで残したディスク
（切り戻した場合のみ）		タグ Purpose = switch-ec2-rollback-preserved必要なデータを取り出し終えたら

これらは消し忘れやすいので、作業完了時のチェックリストに入れてください。実際に、過去の検証で作られたディスクが消されないまま残っていた例があります。

用語集

用語意味
AMIEC2 を起動するときの「型」。OS の内容とライセンス種別を持っています
EBS（ボリューム）EC2 に接続するディスク。OS もデータもここに入っています
ENI（ネットワークインターフェース）EC2 のネットワークカード。IP アドレス・MAC アドレス・セキュリティグループを持っています
スナップショットEBS のバックアップ。AMI の実体はスナップショットの集まりです
UsageOperation課金コード。どのライセンスで課金されるかを表します。起動時の AMI で決まり、後から変更できません
PAYG従量課金のライセンス。時間単位でライセンス料が課金されます
ELCExtended Life Cycle。延長サポート契約のライセンス
DeleteOnTermination「EC2 を削除したらこのディスク／ネットワークカードも一緒に削除する」という設定。このツールは削除前に必ずこれを OFF にします
terminateEC2 の削除。停止（stop）と違い、元に戻せません
CloudShellAWS のブラウザ上で使えるターミナル。このツールの実行環境です
cloud-initEC2 の初回起動時に初期設定を行う仕組み。インスタンス ID が変わると「新しいサーバー」と判断して再実行されます
