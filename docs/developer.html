開発者向け

switch-ec2 開発者ドキュメント

RHEL PAYG の EC2 を ELC/BYOS 系 AMI 起動の EC2 へ置き換える bash スクリプト群の、内部構造・設計判断・失敗モデルの解説。

原理と方式

解決したい課題

EC2 の課金コード（UsageOperation）は RunInstances 時に指定した AMI で確定し、以後変更できない。稼働中インスタンスのライセンス種別だけを変える API は存在しない。

方式

この性質を逆手に取る。「器（インスタンス）を新しく作り、中身（EBS・ENI）を移設する」。

  1. 切替先ライセンスの AMI から新 EC2 を起動 → この瞬間に課金コードが確定する
  2. 新 AMI 由来のルートボリュームをデタッチして破棄予定にする
  3. 旧 EC2 の全 EBS（OS ディスク含む）と全 ENI を新 EC2 へ付け替える

保証される性質と、その根拠

性質根拠
OS・データが完全に同一EBS ボリュームを再作成せず現物を移設する
ファイルシステム UUID が不変同上。fstab の UUID マウントが壊れない
プライマリ／セカンダリ IP・MAC が不変ENI ごと移設する
Elastic IP が不変EIP は ENI に紐付くため ENI 移設に自動追随する
SG が不変SG は ENI の属性
タグ・インスタンスタイプ・IAM ロール等01 で保存した値を 03 の run-instances 引数で再指定する

方式上、避けられない制約

旧 EC2 の terminate は必須

プライマリ ENI（DeviceIndex 0）は running/stopped のインスタンスから単独デタッチできない。同一 IP を引き継ぐ手段は旧 EC2 の terminate 以外に存在しない。03_switch.sh:265

  • インスタンス ID が変わる。cloud-init が新規インスタンスと判定するため、OS 内の事前対策（ssh_deletekeys: false / preserve_hostname: true）が必要
  • 切替後は RHUI が使えない。PAYG 用リポジトリは ELC インスタンスで認可されず 403 になる。サブスクリプションの再登録が必須（本案件では Satellite を使用。手順は別途）
  • 自動割り当てパブリック IPv4 は引き継げない。EIP のみが維持される。検証項目にも含まれない

踏まえておくべき落とし穴

1. run_targets を条件文脈で呼んではいけない

bash の errexit は if／|| の条件文脈でサブシェルへの抑止が伝播し、途中失敗を見逃す。run_targets は必ず main から直接呼ぶこと。lib/common.sh 内にコメントで明記されている。

2. die は return であって exit ではない

set -e が無効化された文脈（条件式の中など）で die を呼ぶと処理が止まらない。新規コードを足すときは呼び出し文脈に注意すること。

3. 状態ファイルの JSON 検査は false/null を特別扱いする

jq -e . は false と null に対して終了コード 1 を返す。状態ファイルには disable_api_termination.json（bool）や cpu_options.json（null あり）が含まれるため、この 2 値を正当値として補完するロジックが必要。03_switch.sh:143-157

if ! jq -e . "$dir/$file" >/dev/null; then
  jq -e 'select(. == false or . == null) | true' "$dir/$file" >/dev/null \
    || die "状態ファイルが有効な JSON ではありません: $dir/$file"
fi

ログと時間計測

形式は [日時] [+経過秒] [LEVEL] [対象ID] メッセージ。_log_raw は tee を使わず printf ... >> file で即時追記する（PIPE_BUF 以下ならほぼ原子的という前提で、並行書き込み時のロックを避ける設計）。

即時追記であることは中断時の唯一の手がかりになる。プロセスが強制終了しても、完了したステップまでのログは必ずファイルに残る。

05_rollback.sh の内部

採用方式：AMI スナップショットからの完全復元（方式B）

バックアップ AMI の BDM をそのまま使って起動する。全 EBS は AMI のスナップショットから新規作成され、ELC 新 EC2 に付いていた保全済み旧 EBS は使わずに available で残置する。ENI は保全済みのものを DeviceIndex 維持で再利用して IP を維持する。

方式B を選んだ結果

  • データは AMI 取得時点まで巻き戻る（切替後の書き込みは失われる）
  • 03 のステップ7〜9（停止→ルート差し替え→再アタッチ）が不要。起動 1 回で完了する
  • デバイス名は AMI 由来＝旧 EC2 と同じなので、ルート名の読み替えが不要
  • ボリューム ID が必ず変わるため、検証ロジックが 04 と別物になる

UsageOperation が戻る理由

バックアップ AMI は 02_backup.sh が旧 PAYG インスタンスから create-image したものなので、その AMI から起動すれば課金コードは自動的に PAYG に戻る。

05 の preflight は起動前に describe-images の UsageOperation が usage_operation.json と一致することを確認する。「この AMI で本当に PAYG に戻れるか」を破壊操作の前に検証している。

ステップ3 のアサート（05 の心臓部）

プライマリ ENI の DOT が true のまま terminate すると IP が永久に失われる

03 は modify を発行するだけで結果を確認していない。05 では発行後に describe-instances と describe-network-interfaces の両方を読み直して検証し、1 つでも true なら terminate 前に die する。05_rollback.sh:294-306

jq -e '[.Reservations[0].Instances[0].NetworkInterfaces[].Attachment.DeleteOnTermination]
       | all(. == false)' <<<"$current_desc" >/dev/null \
  || die "ENI の DeleteOnTermination=false 化に失敗。terminate を中止します。IP 喪失を防ぐためです。"

現物ベースの列挙（追加ボリューム対策）

05 は 03 と違い、ELC で本番稼働したあとに実行される。運用中の構成変更（障害調査用ボリュームの追加など）が入っている確率が高い。

そのため DOT=false 化とデタッチのループは block_devices.json の固定リストではなくその時点の describe を列挙して回す。block_devices.json に無い追加ボリュームを見逃すと、DOT=true のまま terminate に巻き込まれてサイレントに削除されるため。

追加ボリュームを検出したときの既定は die。環境変数 ROLLBACK_ALLOW_EXTRA_VOLUMES=true のときだけ警告して続行し、DOT=false 化とデタッチは行うがロールバック用タグは付けない（オペレータの個別判断に委ねる）。

保全 EBS のタグ

Key=Purpose,Value=switch-ec2-rollback-preserved
Key=DeleteAfterVerification,Value=true
Key=Warning,Value=DO-NOT-ATTACH-DUPLICATE-FS-UUID
Key=SourceOldInstanceId / RolledBackFromInstanceId / RollbackInstanceId

Warning タグの理由：スナップショットはブロックレベルコピーなので、復旧 EC2 のボリュームと保全 EBS はファイルシステム UUID が完全に同一になる。データ救出目的で同一インスタンスにアタッチすると UUID 重複でマウント不能・誤マウントを起こす。

Purpose の文字列は 05 と 06 で共有される

05 が書き、06 が照合する。共通ライブラリを新設しない方針のため、両スクリプト冒頭で ROLLBACK_PRESERVED_PURPOSE として変数定義し、相互参照コメントで担保している。片方だけ変えると検証が空振りする。

04 / 06 の検証ロジック

両者とも report_pass / report_fail / report_info / json_equal をスクリプト内に private に持つ（lib/common.sh には無い）。verify_failed はファイルスコープのグローバルで、run_targets が対象ごとにサブシェルで実行するため対象間で自然にリセットされる。

安全ガードと不変条件

terminate 前に必ず成立していること

  1. 全 EBS と全 ENI の DeleteOnTermination=false が設定済み（05 はさらに実測アサート）
  2. 全 EBS がデタッチされ available（terminate の暗黙デタッチに依存しない二重防御）
  3. preflight とドリフト検査を通過している

状態ファイルは「識別できなくする操作」の前に書く

この順序が中断耐性の根幹

03 のステップ8 が典型例。デタッチしてタグを付ける前に ID をファイルへ落とす。逆順だと、デタッチ直後に中断された場合に「タグも無い available なボリューム」が正体不明で残る。03_switch.sh:394-396

printf '%s\n' "$new_root_device"  > "$dir/new_root_device_name.txt"
printf '%s\n' "$discard_volume"   > "$dir/discarded_root_volume_id.txt"
aws_json ec2 detach-volume --volume-id "$discard_volume" ...   # ← 書き込みの後

05 も同様に、デタッチ前に rollback_preserved_volume_ids.txt を書く。

client token による冪等化

run-instances のレスポンスを受け取る直前で落ちると、状態ファイルに記録されていないインスタンスが存在しうる。client token（switch-ec2-<旧ID> / switch-ec2-rollback-<旧ID>）があるため、describe-instances --filters Name=client-token,... で特定でき、同じトークンでの再発行も二重起動にならない。

失敗モデル（中断耐性）

CloudShell のセッションタイムアウトが現実的な脅威

CloudShell はキーボード・ポインタ操作がない状態が約 20〜30 分続くとセッションを終了し、プロセスの実行は「操作」とみなされない。03 は 1 台あたり 7〜11 分かかるため、実行中に強制終了されうる。nohup／tmux はコンテナ停止には耐えられない。

中断時に注意が必要な 3 点

1. ERR トラップはキルでは発火しない

03/05 が持つのは ERR トラップだけで、HUP/TERM/INT のトラップは無い。セッション終了はシェルのエラーではないため restore_old_protection_on_error は一切走らず、保護属性が解除されたまま放置される。再接続後に手動で戻す必要がある。

2. ステップ11 の中断は 05 をブロックする

new_instance_after_switch.json はステップ11 の最後（最長 178〜260 秒のステップの後）に書かれる。ここで中断されると、切替自体は完了しているのに 05 の preflight が起動を拒否する。04 で完了を確認したうえで describe-instances の結果を手動で保存すれば解消する。

3. WORK_DIR が $HOME 配下にあること

CloudShell で永続化されるのは $HOME（リージョンごと 1GB）だけ。WORK_DIR の既定は ./work でカレントディレクトリ相対のため、/tmp 等で作業すると状態ファイルごと消える。これが CloudShell 運用の単一障害点。

再実行は「安全に死ぬ」

運用ルールとしては「中断後はそのまま再実行しない」が正しいが、実装上は誤って再実行しても壊れない。

  • ステップ4 以降で中断 → ドリフト検査が「EBS 構成が変更されている」で die（デタッチ済みボリュームが BlockDeviceMappings から消えているため）
  • terminate 後に中断 → stop-instances が terminated インスタンスで失敗、または instance_state_is が終端状態を検知して die
  • ステップ3 の途中で中断 → 全操作が冪等なので普通に通る

つまり「再実行して良い場合は通り、いけない場合は破壊前に止まる」。ドリフト検査が意図せず安全網として機能している。

設計判断とその理由

判断理由
自動リランに対応しないterminate を挟む処理の途中再開は、状態の組み合わせが多すぎて安全に自動判定できない。人間がログと現物から到達位置を判断する方が確実
DOT=false → デタッチ → terminate の順序terminate の暗黙デタッチに依存せず、検証可能で決定的な状態を作ってから不可逆操作に入るため
ENI は事前デタッチしないプライマリ ENI は単独デタッチ不可。terminate 後の available 待ちに委ねるしかない
05 は方式B（AMI から完全復元）切り戻しは「切替後に問題が出た」場面。ELC 側のディスクを疑う状況もあるため、既知の正常状態（AMI 取得時点）へ戻す選択。保全 EBS は残すのでデータ救出は可能
05/06 は 01〜04 と lib/common.sh を変更しない01〜04 は本番検証済み。lib/common.sh は 4 本が実行時に source する共通基盤で、構文ミス 1 つで道連れに壊れる。既存コードベース自体が「2 本でしか使わないヘルパは共通化しない」流儀（modify_volume_dot は 03 専用、json_equal は 04 専用）
05 の client token を分離同じトークンだと EC2 の冪等性キーが 03 の起動と衝突し、既存の新 EC2 と同一視される
05 は並行実行を持たない切り戻しは緊急時の操作。中断・失敗時に手動復旧が必要な対象を増やさないことを優先
破棄ルート・保全 EBS を自動削除しない検証完了とデータ救出の判断は人間が行うべき。タグで識別可能にして手動削除に委ねる
OS 内操作を一切行わない実行環境を CloudShell の AWS 権限だけで完結させ、対象 OS の SSH 鍵を持たせないため。OS 内作業は別途の運用手順が担当する

実機で確証が取れたこと

  • UsageOperation が RunInstances:0010（旧 PAYG 値）へ復帰
  • プライマリ IP 維持、ENI が DeviceIndex 0 のまま再利用
  • 復旧ボリュームは新 ID だが SnapshotId がバックアップ AMI の BDM と完全一致（方式B の核心）
  • 保全 EBS が available＋タグ付きで残置、ELC 新 EC2 は terminated
  • 二重実行ガードが AWS を一切変更せず拒否し、失敗時の終了コード 1 も正しく伝播

実機でしか出なかった発見

1. EBS ボリュームのタグは引き継がれない

切替前のボリュームには Name／Project／Env／Owner タグが付いていたが、AMI スナップショットから作られた復旧ボリュームはタグが空だった。create-image はボリュームタグをスナップショットへコピーせず、run-instances も AMI 由来ボリュームにタグを付けない。

ボリュームタグを条件にした AWS Backup・DLM・コスト配分タグを使っている場合は切り戻し後に壊れる。06 はボリュームタグを検証対象にしていないので、手動で before_volumes.json から復元する運用が必要。

2. volumes の Device 差分は並び順の artifact

手動 diff でデバイス名の差分が出るが、これは after_rollback_volumes.json がボリューム ID 順にソートされるため。方式B では全 ID が変わるので、データボリュームが複数あると配列内の順序が入れ替わる。デバイス名の集合が一致していれば正常。

06 はデバイス名で対応付けて比較するため、この並び替えの影響を受けない。

拡張・改修時の注意

触るときに気をつける箇所

  • run-instances の引数組み立ては 03 と 05 で二重化している。属性を追加するときは両方を直すこと。片方だけだと切り戻し後に属性が欠ける
  • ROLLBACK_PRESERVED_PURPOSE は 05（書き手）と 06（読み手）で一致必須。共通ライブラリを持たない設計上の弱点
  • lib/common.sh を変更すると 01〜04 の検証済み前提が崩れる。変更するなら全スクリプトの再検証が要る
  • 新しい引き継ぎ属性を足すときは 01（保存）→ 03/05（再指定）→ 04/06（検証）の 3 か所がセット
  • 述語関数を追加する場合、wait_until の契約（終端到達不能は rc=2）に従うこと。従わないとタイムアウトまで無駄に待つ
